# Отчёты о работе над сайтом

Регламент и инструменты для сборки ежемесячного PDF-отчёта. Цель — чтобы каждый следующий отчёт
получался в том же виде, что и предыдущие, а цифры в нём были посчитаны, а не написаны от руки.

```
tools/reports/
├── build_report.py       # генератор PDF (единственный, для всех периодов)
├── periods/2026-06.json  # конфиг периода — тексты и состав работ
├── periods/2026-07.json
└── out/                  # готовые PDF (в git не нужны)
```

## Как собрать отчёт

```bash
python tools/reports/build_report.py tools/reports/periods/2026-08.json
```

Скрипт печатает путь к PDF и посчитанные метрики. Зависимости: `reportlab` (и `pypdfium2`,
если нужно отрендерить страницы в PNG для проверки вёрстки).

```bash
python -m pip install reportlab pypdfium2
```

## Правило первое: отчётный период ≠ даты коммитов

**Работа месяца попадает в репозиторий в следующем месяце.** Статьи, закоммиченные 6 и 9 июля, —
это работа за июнь. Ориентироваться только на `git log --since/--until` нельзя: так период
сдвинется на месяц.

Порядок действий:

1. Посмотреть коммиты вокруг периода: `git log --pretty=format:"%h|%ad|%s" --date=short`.
2. **Уточнить у заказчика, какие работы относятся к отчётному месяцу**, если границы неочевидны.
3. Зафиксировать в конфиге ревизию, на конец периода (`"source": "git:<хеш>"`).

Мелкие правки, попавшие в период по календарю, но не относящиеся к основной работе (например,
добавление партнёра), выносятся отдельным пунктом в раздел «Прочие работы» с явной датой.

## Правило второе: цифры считаются из данных

Все метрики — количество статей, слов, знаков, иллюстраций, связей с каталогом, время чтения,
названия связанных товаров и услуг — генератор извлекает из `src/data/residentPortalContentData.ts`.
В конфиге их дублировать не нужно и нельзя: расхождение между текстом и таблицей сразу заметно.

Источник данных задаётся полем `source`:

| Значение | Когда использовать |
|---|---|
| `"git:54022d3"` | Прошедший период — берётся состояние файла на конец периода |
| `"working"` | Текущий период, работа ещё не закоммичена |

Для «было / стало» в таблице динамики нужно состояние **до** периода — сравнить вручную:

```bash
git show <ревизия-до-периода>:src/data/residentPortalContentData.ts > /tmp/before.ts
```

и посчитать статьи по направлениям (регулярка `id: '<slug>-kb-\d+'`). Полученные числа
записываются в поле `before` каждого направления — это единственные цифры, вводимые руками.

## Правило третье: структура отчёта

Разделы идут в фиксированном порядке. Необязательные помечены.

1. **Итоги периода** — вводный абзац (`intro`), пять карточек с метриками, уточняющий абзац
   (`summary_note`).
2. **Динамика базы знаний** — таблица «было / добавлено / стало / прирост» по направлениям
   с итоговой строкой. Строится, если у всех направлений задано `before`.
3. **Прочие работы за период** *(необязательный)* — всё, что не статьи: каталог, документация,
   правки, партнёры. Задаётся списком `other_works`.
4. **Как устроены статьи** — методика: почему материалы такие, какие есть. Не менять
   без причины — раздел объясняет заказчику ценность работы.
5. **Перечень опубликованных статей** — одна сплошная таблица с подзаголовками направлений,
   сквозная нумерация, связанные позиции каталога и время чтения.

Разделов с метриками посещаемости в отчёте нет: этих данных в репозитории нет.
Если заказчик попросит — добавлять отдельным разделом с его цифрами, не выдумывая.

## Правило четвёртое: оформление

Менять не нужно — оно единое для всех периодов и уже зашито в генератор.

- Формат A4, поля 18 мм, шрифт Arial (кириллица; DejaVu и встроенные шрифты reportlab не годятся).
- Палитра берётся из `src/index.css`: `#1F2933` (основной), `#2F6FED` (акцент), `#6B7C8F` (текст
  второго уровня), `#F5F7F9` / `#E6EEF8` (заливки), `#D9E1E8` (границы).
- Титульная плашка на первой странице, колонтитул с периодом — на остальных, нумерация страниц сквозная.
- Прямые кавычки `"` в заголовках и анонсах статей автоматически заменяются на «ёлочки»
  (только в отчёте, данные сайта не меняются).
- Длинные таблицы разрываются между страницами, шапка повторяется. Неразрывные блоки
  (`KeepTogether`) для перечня статей не применять — они дают пустоты в треть страницы.

## Правило пятое: проверка перед отправкой

1. Сверить метрики из вывода скрипта с текстом отчёта — плейсхолдеры `{n}`, `{avg}`, `{chars}`,
   `{links}` подставляются автоматически, но остальные числа в тексте написаны руками.
2. Отрендерить страницы и просмотреть их — в первую очередь на пустоты и висячие заголовки:

```bash
python -c "import pypdfium2 as p; d=p.PdfDocument('tools/reports/out/имя.pdf'); [d[i].render(scale=1.6).to_pil().save(f'p{i+1}.png') for i in range(len(d))]"
```

3. Убедиться, что итоговая строка таблицы динамики не осталась одна на второй странице
   (если так — сократить вводные абзацы на пару строк).

## Как завести новый период

1. Скопировать ближайший конфиг: `periods/2026-07.json` → `periods/2026-08.json`.
2. Поменять `period_label`, `period_short`, `compiled`, `output`, `source`.
3. Переписать `intro`, `summary_note`, `dynamics_note`, `hidden_note` под содержание периода.
4. Перечислить направления и id новых статей в `directions`, проставить `before`.
5. Заполнить `other_works`, если помимо статей были иные работы.
6. Собрать, проверить по пункту «Проверка перед отправкой».

### Поля конфига

| Поле | Назначение |
|---|---|
| `period_label` | «июль 2026 года» — на титуле |
| `period_short` | «июль 2026» — в колонтитуле и метаданных PDF |
| `compiled` | дата составления, выводится в подвале первой страницы |
| `source` | `working` или `git:<ревизия>` — откуда брать данные |
| `output` | путь к PDF относительно конфига |
| `intro` | вводный абзац раздела «Итоги»; поддерживает `{n}` |
| `summary_note` | абзац под карточками; `{avg}`, `{chars}`, `{n}` |
| `dynamics_note` | абзац перед таблицей динамики |
| `hidden_note` | сноска под таблицей (общий объём базы с учётом скрытых резидентов) |
| `other_works` | список `[заголовок, текст]`; раздел не выводится, если пусто |
| `method_intro` | вводный абзац раздела «Как устроены статьи» |
| `principles` | список `[заголовок, текст]`; поддерживает `{links}`, `{n}` |
| `directions` | `slug`, `name`, `before`, `articles` — состав периода по направлениям |
